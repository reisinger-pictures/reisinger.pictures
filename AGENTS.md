# Architectural Guidelines, AI Rules & Best Practices

This document summarizes key architectural decisions, toolchains, and workflow rules for the `reisinger.pictures` website project. All contributions and AI-generated code must strictly adhere to these standards.

## 1. AI Agent Roles & Strict Definition of Done (DoD)
We enforce a strict separation of concerns via `AGENTS.todo.md`. An agent must fulfill its specific DoD before completing a turn.
* **Role 1: Planner Agent ("Architect")**
    * **Goal:** Define target state and estimate effort. Update/create Markdown docs in `/features/` (if applicable) or plan the architecture.
    * **DoD:** Concept documented. Actionable tasks appended to `AGENTS.todo.md`.
* **Role 2: Implementation Agent ("Maker")**
    * **Goal:** Execute the top unassigned `[ ] TODO` from `AGENTS.todo.md`.
    * **DoD:** Code is written. Task status changed to `(Ready for Review)`.
* **Role 3: Review Agent ("Checker")**
    * **Goal:** Quality assurance.
    * **DoD:** Code validated. Zero tolerance for workarounds. Task checked off `[x]` in `AGENTS.todo.md`. If failed, change to `(Needs Fix)`.
* **Silent TODO Rule:** Do not log or display TODOs in the chat that you create and immediately complete.

## 2. Language Policy & Code Quality
* **Language:** Technical Content (Code, Docs, Variables, Comments) = **English**. User Interface (Strings, Menus, Content) = **German**.
* **Centralized Logic:** Math and calculation logic (e.g., pricing formulas) MUST reside in `src/content/pricing.ts` to ensure consistency between SSR and Client-side islands. Do not duplicate logic.
* **Dead Code:** Remove unused functions and styles entirely.

## 3. Frontend & Architectural Standards
* **Styling:** Strictly use Tailwind CSS (v4) and DaisyUI. Do not write custom CSS in `<style>` blocks.
* **Component Separation:** * Static UI & Layouts: `.astro` components in `src/layouts/`.
    * Reactive Islands: `.tsx` components using **SolidJS** must be placed in `src/solid/`. Do not use React.
* **Hydration Strategy:**
    * Use `client:visible` for all SolidJS components below the fold.
    * Use `client:load` only for critical interactive elements at the top.
* **UI/UX:** Provide clear feedback (Toasts). CTA buttons in cards must be pushed to the bottom using `mt-auto`. No loading skeletons for SSR components.
* **Images:** NEVER use standard `<img>`. Always use the custom `ResponsiveImage.astro` for EXIF handling, responsive sizes, and optimization.
* **UI review:** the `ui-review` screenshot/vision pass is required for technical and UI changes (components, styling, layout, hydration). It is **not** required when a change only adds or edits content (blog article, images, copy) — a green build plus `check_links` is the verification there.

## 4. Event Blog Articles (Images, Captions, Review)
Event articles (`src/content/portfolio/**/index.mdx` plus image YAML sidecars) follow the **`blog-beitrag` skill**. That skill is the single source of truth for the workflow: context gathering, vision analysis, the `review.json` / `review.html` review, renames, `index.mdx`, metadata generation, build verification. Do not restate or improvise that workflow here.
The invariants that hold for the whole project, including every other content type:
* **HITL gate:** No rename, YAML sidecar, `index.mdx` or slug reference may be written before the viewer-based review of the affected images is complete.
* **Division of labour:** the agent writes only `description` into a YAML sidecar. `slug`, `metadata` and `categories` are generated by `add-metadata.mjs` (runs as `prebuild` hook). Never hand-write EXIF values into YAML.
* **Schema first:** `review.json` must pass `pnpm run review:validate` against `schemas/review.schema.json` before `review:apply` runs.
* **Image rendering:** published images go through `ResponsiveImage.astro` / the Gallery component. The standalone `review.html` is the only `<img>` exception, because it loads local review images directly.
* **Local review data:** `review*.json` is local and must never be committed; `review.html` is the committed viewer.

## 5. Build Cache & Asset Hygiene
* **Never delete cache directories:** `.cache/`, `.astro/` and `dist/` are managed by Astro. They must **never** be deleted on your own initiative – neither partially nor completely.
* **Consequences:** deleting them corrupts image-hash references, causes build failures with `ENOENT` errors, and forces unnecessary full recomputations.
* **Instead:** run `astro sync` to update the content index. Ask the user about real cache problems.
* **dist/ is a build artifact:** `astro build` rewrites `dist/` completely. Never commit or reference changes inside it.

## 6. Deployment & Hosting Strategy
* **Architecture:** SSG Astro site, hosted via Nginx in a Portainer Docker stack.
* **Sync:** The local build is uploaded with rsync over ssh by `apps/reisinger.pictures/sync.sh` — `.imagedist/` to the image CDN, `dist/` to the website.
* **Publishing:** the complete build and sync cycle is orchestrated via `pnpm run publish` (this project uses **pnpm**, not npm; `prebuild`, `postbuild` and `postpublish` hooks run automatically). Never run publishing or deployment commands unless the user explicitly asks for publication. Do not introduce GitHub Actions CI/CD unless explicitly requested.

## 7. Rules & Edge Cases
* **Consult first:** for unclear structures, data mappings or naming conventions, always read the Markdown files in `rules/` first.
* **Extend immediately:** whenever development produces a new edge case, conflict (e.g. about URLs or labels) or architecture decision, a rule **must** be documented in `rules/` immediately, or an existing rule extended.
* **Maintain skills:** skills are managed via symlink in the global skill folder (`~/.agents/skills/`). Changes to content structures, naming conventions or the caption/review flow must be applied to the affected skill immediately.
* **Goal:** a consistent, self-documenting system that every AI agent can understand and continue.
