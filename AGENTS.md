# Project Rules

This file contains only durable, reusable rules for the `reisinger.pictures` project. All contributions and AI-generated code must follow them.

## 1. Scope and Maintenance
* **Rules only, no decisions:** This file contains rules only — instructions that apply to any work in this repo. Durable decisions, rationale, measurements and history do not belong here but in `rules/` (or the project docs); open work goes to `AGENTS.todo.md`, settled matters to git history.
* Keep `AGENTS.todo.md` limited to open work. Put architectural decisions, factual mappings and lasting edge cases in `rules/`; put repeatable procedures in the relevant skill. Link to those sources instead of duplicating their contents here.
* User-commissioned changes in this Git repository follow the global `build-verify` skill. Do not maintain a competing agent-role or completion-status workflow in this file.
* Remove or update obsolete rules when the project structure or toolchain changes.

## 2. Language Policy & Code Quality
* **Language:** technical content (code, docs, variables, comments) = **English**; user interface (strings, menus, content) = **German**.
* **Centralized logic:** math and calculation logic (e.g. pricing formulas) MUST reside in `src/content/pricing.ts`; never duplicate it between SSR and client-side islands.
* **Dead code:** remove unused functions and styles entirely.

## 3. Frontend & Architectural Standards
* **Styling:** use Tailwind CSS (v4) and DaisyUI only; no custom CSS in `<style>` blocks.
* **Component separation:** static UI and layouts are `.astro` components in `src/layouts/`; reactive islands are SolidJS `.tsx` components in `src/solid/`. Do not use React.
* **Hydration:** `client:visible` for all SolidJS components below the fold; `client:load` only for critical interactive elements at the top.
* **UI/UX:** give clear feedback (toasts); card CTA buttons sit at the bottom via `mt-auto`; no loading skeletons for SSR components.
* **Images:** never use a plain `<img>`; always use `ResponsiveImage.astro` (EXIF, responsive sizes, optimization).
* **UI review:** the `ui-review` screenshot/vision pass is required for technical and UI changes (components, styling, layout, hydration). It is **not** required when a change only adds or edits content (blog article, images, copy) — a green build plus `check_links` is the verification there.

## 4. Event Blog Articles (Images, Captions, Review)
Event articles (`src/content/portfolio/**/index.mdx` plus image YAML sidecars) follow the **`blog-beitrag` skill**, the single source of truth for that workflow. Do not restate or improvise it here.
The following invariants hold for the whole project, including every other content type:
* **HITL gate:** no rename, YAML sidecar, `index.mdx` or slug reference before the viewer-based review of the affected images is complete.
* **Division of labour:** the agent writes only `description` into a YAML sidecar; `slug`, `metadata` and `categories` are generated by `add-metadata.mjs` (a `prebuild` hook). Never hand-write EXIF values into YAML.
* **Schema first:** `review.json` must pass `pnpm run review:validate` against `schemas/review.schema.json` before `review:apply` runs.
* **Image rendering:** published images go through `ResponsiveImage.astro` / the Gallery component; the standalone `review.html` is the only `<img>` exception, because it loads local review images directly.
* **Local review data:** `review*.json` is local and must never be committed; `review.html` is the committed viewer.

## 5. Build Cache & Asset Hygiene
* **Never delete cache directories:** `.cache/`, `.astro/` and `dist/` are managed by Astro; never delete them on your own initiative — neither partially nor completely. Rationale in `rules/14-build-cache.md`.
* **Instead:** run `astro sync` to update the content index; ask the user about real cache problems.
* **`dist/` is a build artifact:** `astro build` rewrites it completely; never commit or reference changes inside it.

## 6. Deployment & Hosting Strategy
* **Architecture:** SSG Astro site, hosted via Nginx in a Portainer Docker stack; the image CDN is documented in `rules/03-image-cdn-caddy.md`.
* **Sync:** `apps/reisinger.pictures/sync.sh` uploads the local build with rsync over ssh — `.imagedist/` to the image CDN, `dist/` to the website.
* **Publishing:** the full build-and-sync cycle runs via `pnpm run publish` (this project uses **pnpm**, not npm; the `prebuild`, `postbuild` and `postpublish` hooks run automatically). Never run publishing or deployment commands unless the user explicitly asks.
* **CI/CD:** do not introduce GitHub Actions CI/CD unless explicitly requested. The one workflow of this repository is `.github/workflows/ratchet.yml` — the gates of `rules/15-ui-findings-gate.md`, commissioned explicitly.

## 7. Rules & Edge Cases
* **Consult first:** for unclear structures, data mappings or naming conventions, read the Markdown files in `rules/` first.
* **Extend immediately:** whenever work produces a new edge case, conflict (e.g. about URLs or labels) or architecture decision, document it in `rules/` immediately, or extend an existing rule.
* **Maintain skills:** skills are managed via symlink in the global skill folder (`~/.agents/skills/`). Apply changes to content structures, naming conventions or the caption/review flow to the affected skill immediately.
